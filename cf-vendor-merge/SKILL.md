# /cf-vendor-merge — обновление доработанной конфигурации на новый релиз

Скрипты: `.agents/skills/cf-vendor-merge/scripts/` (Python 3 + `lxml`). Грабли и решения — `references/gotchas.md`, прочитай до начала.
Все скрипты работают с рабочим каталогом слияния `<work>` и файлом состояния `<work>/vendor-merge.json`.

## Что нужно от пользователя

1. Полные `.cf`/`.dt` **старого** релиза (на котором стоит текущая конфигурация — версия в `Configuration.xml` текущей выгрузки) и **нового** релиза. `.cfu` не подходит.
2. Текущая конфигурация: XML-выгрузка (каталог) или ревизия в git, либо база, из которой выгрузить (`/db-dump-xml`).
3. `ibcmd.exe` (из `.v8-project.json` → `v8path`), каталог для временных баз не в облачной папке, ~25+ ГБ свободно.
Рабочую базу не трогай: результат проверяется на временной/копии; загрузка в рабочую — только по прямой команде.

## Этап 1. Выгрузки и ветки

```
python vm_dump.py --ibcmd <ibcmd> --src <старый.cf> --out <tmp>\old_xml
python vm_dump.py --ibcmd <ibcmd> --src <новый.cf>  --out <tmp>\new_xml --keep-db
python vm_branches.py --repo <git-репозиторий> --work <work> --old-xml <tmp>\old_xml --new-xml <tmp>\new_xml (--custom-xml <каталог> | --custom-rev <ревизия>) [--root <коммит с .gitattributes>] [--gitattributes <файл>]
```
Сверь версии, которые печатают скрипты: старый релиз = версия поставщика в текущей конфигурации; формат выгрузки одинаковый. Ветки: `vendor-<старая>`, `vendor-<новая>`, `custom` (дерево текущей, родитель — старый релиз). Заданный `VM_COMMIT_TRAILER` (например, `\n\nCo-Authored-By: ...`) добавляется к сообщениям коммитов.

## Этап 2. Слияние и автоматический разбор

```
python vm_merge.py --work <work>                     # git merge -X no-renames, conflicts.json
python vm_resolve_md.py --work <work> [--apply]      # modify/delete: шум -> принять удаление поставщика
python vm_xmlmerge.py --work <work> [--apply]        # структурное слияние XML (без Template.xml)
python vm_templates.py --work <work> [--apply]       # макеты: целиком наш/поставщика по правилам
```
Каждый скрипт сначала запускай без `--apply`, смотри отчёт/лог, затем с `--apply`.
Решения человека (через AskUserQuestion, с рекомендацией):
- `REAL deleted_in_theirs` — поставщик удалил файл с настоящей доработкой; `ORPHAN` — наша форма/модуль в удалённом поставщиком объекте (обычно удалить вместе с объектом);
- конфликты `add/add` объектов верхнего уровня с разным UUID — по умолчанию наш объект переименовать в `Удалить*` (данные сохраняются), поставщика взять как есть, добавить строку в `Configuration.xml`; затем `vm_check.py ours-renamed` (этап 4) — иначе `Удалить*` выпадет из определяемых типов и типов полей, и при обновлении БД его данные (записи регистров по этим полям) будут удалены;
- `manual` у макетов — обычно наш макет + перенос новых параметров поставщика через `edit_template`.
`CONFLICT ...` в `xmlmerge.log` — просмотри: чаще всего это шум, но проверь.

## Этап 3. BSL — параллельные агенты

```
python vm_bsl_plan.py --work <work> --groups 4
```
Скрипт пишет инструкцию `<work>/bsl_instructions.md` (из `references/bsl-merge-agent.md`) и списки групп и печатает готовые тексты заданий — запусти агентов (Agent, `general-purpose`, в фоне) по одному на группу. Пока они работают, займись этапом 4 для XML.
После отчётов: проверь каждый файл (нет маркеров, BOM, CRLF, `git diff <theirs> -- <файл>` содержит только доработки), примени переносы «в другой модуль» из отчётов сам, `git add`.

## Этап 4. Проверки до коммита

```
python vm_check.py --work <work> automerged       # то, что git склеил сам: XML, id форм, баланс BSL
python vm_check.py --work <work> refs             # ссылки на отсутствующие объекты/реквизиты, состав Configuration.xml, подсказки переименований
python vm_check.py --work <work> roles-clean --apply
python vm_check.py --work <work> ours-renamed      # наши объекты Удалить*: выпали ли из типов, где лежат данные
```
`roles-clean` права на переименованные поставщиком объекты и поля, сменившие вид, переименовывает, на отсутствующее — удаляет; сначала запусти без `--apply` и просмотри.
Ссылки на переименованные поставщиком объекты — переименуй (подсказка `-> переименован в`), на удалённые — убери. Когда `git diff --name-only --diff-filter=U` пуст и проверки чистые — коммит слияния в ветке `custom`.

## Этап 5. Импорт в пустую базу

```
python vm_import.py --work <work> --ibcmd <ibcmd>
```
Итерации по 5–8 минут: первый проход (XDTO) падает на первом сломанном файле, второй выдаёт полный список. Чини, коммить, повторяй до `Импорт успешен`.

## Этап 6. check_code и расширения

```
python vm_check.py --work <work> cc-lists --groups 4 --check-base <каталог базы с src/cf> [--extension <каталог расширения>]...
python vm_cfe.py --work <work> --cfe <каталог расширения> [--cfe ...]
```
`cc-lists` печатает задания агентам для `check_code` (MCP `1c-form-viewer`): наши новые модули целиком, изменённые типовые — только строки доработок; инструкция — `references/check-code-agent.md`. Модули расширений проверяй тем же способом (список `cc_ext_*.txt`).
`vm_cfe.py` — без агентов: заимствования (удалены/переименованы; формы без `ExtendedConfigurationObject` молча отвязываются при загрузке — `--fix-eco`), перехватчики (метод перенесён, параметры, `&ИзменениеИКонтроль` «метод изменён» с diff поставщика, `&Вместо` без `ПродолжитьВызов`), вызовы общих модулей, изменившиеся базовые формы. Исправления в расширении — `cfe-patch-method`, `cfe-borrow`, затем `cfe-validate`.
