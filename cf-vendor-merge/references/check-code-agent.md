# Пакетная проверка модулей через check_code после обновления

Конфигурация (результат слияния): `{{REPO}}`. Ревизии: `{{BASE}}` — старый типовой, `{{OURS}}` — конфигурация заказчика до обновления, `{{THEIRS}}` — новый типовой, `HEAD` — результат.

## Что делать

Файл-список: строка `<абсолютный путь .bsl>\t<диапазоны строк>`.

1. Загрузи инструмент: `ToolSearch` → `select:mcp__1c-form-viewer__check_code`.
2. Для каждой строки вызови `check_code` с `path` из списка и `base` = `{{CHECK_BASE}}` (расширения из src/cfe читаются автоматически):
   - диапазоны пустые — проверяй модуль целиком;
   - диапазоны заданы (`a-b,c-d`) — это строки, отличающиеся от нового релиза (доработки); проверяй модуль целиком и оставляй только ошибки в этих диапазонах (±2 строки);
   - постраничный результат (`cursor`) — дочитай.
3. Независимые вызовы — параллельно, пачками по 8–10.

## Отбор

- Отчитывайся об ошибках `kind` = `compile`, `runtime`, `context`.
- `source: platform` (синтакс-помощник с пробелами) — включай с пометкой «низкая уверенность».
- `source: form` (элемента нет в Form.xml, код может создать его программно) — отдельной сводкой: файл + имена.
- Причина каждой ошибки: (а) поставщик удалил/переименовал метод, объект, реквизит или изменил сигнатуру — сверь `git -C "{{REPO}}" grep -n "<имя>" {{BASE}}` и `{{THEIRS}}`, найди замену; (б) ошибка была и до обновления (ссылки не было и в `{{OURS}}`); (в) прочее.
- Ничего не исправляй, файлы и git не трогай.

## Результат

1. TSV (путь дан в задании): `файл\tстрока\tkind\tsource\tсообщение\tпричина(а/б/в)\tзамена/комментарий`.
2. Последнее сообщение — по-русски, кратко: сколько модулей проверено; ошибок по категориям; полный список (а) с предлагаемой заменой; (б) — числом и 3–5 примеров.
