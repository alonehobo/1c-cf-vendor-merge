# Перенос доработок в модули нового релиза

Репозиторий выгрузки 1С: `{{REPO}}` (идёт незавершённое слияние).

Ревизии:
- `{{BASE}}` — старый типовой релиз (BASE);
- `{{OURS}}` — текущая конфигурация заказчика = BASE + доработки (OURS);
- `{{THEIRS}}` — новый типовой релиз (THEIRS).

Назначенные файлы в рабочем каталоге содержат маркеры конфликта diff3. Не склеивай маркеры текстом: поставщик мог сильно переработать модуль, и построчное выравнивание git там бессмысленно.

## Метод для каждого файла

1. Доработки: `git -C "{{REPO}}" diff {{BASE}} {{OURS}} -- "<путь>"`. Каждый hunk — доработка. Бывают с пометками (комментарии с фамилией/датой/фирмой, префиксы своих объектов), бывают без.
2. Основа — версия нового релиза: `git -C "{{REPO}}" show :3:"<путь>"` → записать в файл байт-в-байт (UTF-8 с BOM, CRLF). Если `git checkout --theirs` доступен — можно им.
3. Перенеси каждую доработку по смыслу в правильное место новой версии, минимально трогая типовой код, сохраняя пометки.
   - Типовой код вокруг доработки переписан — адаптируй (новые имена переменных/процедур, новые поля и колонки запросов, например обязательные в новом релизе колонки объединения).
   - Мы закомментировали/изменили типовую строку, а поставщик её тоже изменил — реши, нужна ли доработка в новом коде; при сомнении сохрани поведение заказчика и пометь `// TODO-MERGE: <пояснение>`.
   - Поставщик сам реализовал то же — не переноси, укажи в отчёте как устаревшую.
   - Типовой код переехал в другой модуль (часто: общий модуль разбит на несколько, печать вынесена в *Локализация) — НЕ правь другие файлы; опиши в отчёте модуль, процедуру, строку и точный код переноса.
   - Вызывается метод, которого в новом релизе нет или у которого изменилась сигнатура, — найди замену: `git -C "{{REPO}}" grep -n "<имя>" {{THEIRS}} -- "*.bsl"`; нет замены — `// TODO-MERGE`.
   - Только пробелы/форматирование — не переноси.
4. Проверь: нет маркеров `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`; сбалансированы `#Область`/`#КонецОбласти`, `#Если`/`#КонецЕсли`, процедуры/функции; нет дублей имён методов; BOM и CRLF на месте.
5. Если доступен MCP `1c-form-viewer` — прогони `check_code` по перенесённым фрагментам (`path` + `lines`).

## Правила

- Правь только назначенные файлы.
- Инструмент Edit может срезать пробелы в конце строк и портить типовые строки — для больших вставок используй байт-точный скрипт (Python: читать/писать bytes, сохранять BOM и `\r\n`), затем сверяй `git diff {{THEIRS}} -- <файл>`: должны остаться только твои вставки.
- Не выполняй `git add`, `git commit`, `git merge`, `git reset`, `git checkout` чужих путей. Разрешено: `git diff`, `git show`, `git grep`, `git log`, `git checkout --theirs -- <назначенный файл>`.
- Испортил файл — восстанови конфликт: `git -C "{{REPO}}" checkout --conflict=diff3 -- "<путь>"`.
- Поиск по конфигурации — через `git grep` по нужной ревизии, а не обходом файловой системы.
- Код заказчика обращается к реквизитам/элементам формы, которых нет в Form.xml ни у заказчика, ни в новом релизе, — это существовавшая до обновления проблема (или элементы создаются программно/расширением): перенеси как есть и упомяни в отчёте.

## Отчёт (последнее сообщение, по-русски, кратко)

По каждому файлу: сколько доработок было и перенесено; что адаптировано (строка на случай); что не перенесено как устаревшее и почему; все `TODO-MERGE` с номером строки; что перенести в другие модули (путь, процедура, код). Отдельно — зависимости от метаданных заказчика (реквизиты, регистры), которые должны прийти слиянием XML.
